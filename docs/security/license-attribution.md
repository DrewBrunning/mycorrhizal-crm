# License attribution for distributed artifacts (issue #1880)

## Decision

**Attribution is owed** for both binary artifacts this project distributes:

- the all-in-one container image (`docker-publish.yml`), and
- the Android APK/AAB (`android-apk-build.yml`, `android-aab-build.yml`, and
  the F-Droid recipe).

Both bundle third-party code under permissive licenses (MIT, ISC, BSD,
Apache-2.0, MPL-2.0) whose conditions include reproducing the copyright notice
and license text in the distributed artifact or its documentation. The
existing Trivy license scan (`license-compliance.yml`) answers a different
question — *may* we ship this dependency — and does not assemble notices.

Recorded for `v1.5.1` in issue #1880.

## Scope

The notice covers the third-party **application dependencies** that are compiled
or bundled into each artifact:

| Artifact | Dependency set | Generated by |
|---|---|---|
| Container | Go modules linked into the backend binary; npm production packages bundled into the SPA | `backend/cmd/gennotices` → `THIRD_PARTY_NOTICES.md` |
| Android APK/AAB | Gradle `release` runtime classpath | AboutLibraries at build time → in-app **Settings → About → Third-party licenses** |

The container's Alpine base layer is an unmodified upstream distribution. Its
installed package inventory (including license identifiers) is present in the
image at `/lib/apk/db/installed`; the application notice does not restate it.
Changing the base image or the `apk add` list is still a distribution change and
belongs in the same review as this notice. **This is a manual-review
boundary, not an automated gate:** the drift check below compares only the Go
and npm dependency graphs the image links or bundles, and a Dockerfile/base
image/`apk add` edit cannot make `THIRD_PARTY_NOTICES.md` stale. The `notices`
filter in `.github/filters.yaml` therefore deliberately does not match
`Dockerfile` or `docker/**` (issue #1944) — a match would run a check that
cannot fail on the change. A reviewer must read those diffs against this
section.

## Container: generated file, drift-gated

`THIRD_PARTY_NOTICES.md` is generated, not hand-authored:

```bash
cd backend && go run ./cmd/gennotices
```

- **Go**: `go list -deps .` enumerates exactly the modules linked into the
  `mycorrhizal` binary (not `./...`, which would include test-only packages),
  then reads each module's top-level `LICENSE*`/`COPYING*`/`NOTICE*` files.
- **npm**: the pinned `license-checker-rseidelsohn` dev dependency reads
  production `node_modules` and each package's license file. A package with no
  license file falls back to the bundled SPDX text in
  `thirdparty/licenses/`; an unknown license fails generation rather than
  silently omitting attribution.

Generation executes local tools (`go list` and the repo-local checker). That is
build-time tooling, not a server or request path; the `os/exec` scope and its
threat reasoning are recorded in `docs/security/asvs-l2.md` P12 (issue #1943).

The file is copied into the image (`/app/THIRD_PARTY_NOTICES.md`) and served at
`/third-party-notices.txt`. Because it is committed and consumed by the
Dockerfile, the release build ships it; no release-only generation step can
disagree with it.

Drift is gated in `unit-tests.yml`'s `Docs & security-doc citations` job, step
`Verify third-party notices are current` (issue #1944). That job is a required
merge-blocking status check (`.github/rulesets/main-protection.json`) and a
mandatory per-PR release gate (`.github/release-gates.json`), so a stale notice
cannot merge. The step regenerates from the resolved dependency graph and fails
if the committed file differs. It is path-gated by `.github/filters.yaml`'s
`notices` filter — a dependency-manifest change, a change to the generator or
its license-text fallbacks, or the committed notice itself. Nightly runs and
the release composition's dispatch/call paths run it unconditionally. The diff
on a dependency PR is the review artifact; unrelated PRs pay only for the
citation checks, not the dependency install.

The check used to live in `license-compliance.yml` (PR #1942), whose jobs carry
no required status check; it was advisory there. Issue #1944 moved it into the
already-required job rather than creating a new required context, per
`CLAUDE.md`'s "Adding a quality gate".

## Android: GMS-free in-app surface

The app applies AboutLibraries' Android Gradle plugin (version 14.2.x, the
Compose 1.10 / AGP 9 line that matches this project's Kotlin 2.3 toolchain). It
collects the `release` dependency graph at build time into
`res/raw/aboutlibraries.json`; `feature:settings` parses that data with
`aboutlibraries-core` and renders it under **Settings → About → Third-party
licenses**. Expanding a library shows its full license text.

This deliberately does **not** use Google's `oss-licenses-plugin` /
`play-services-oss-licenses`: that pulls GMS into every flavor and would break
the `foss` flavor's documented zero-`com/google/android/gms` guarantee
(`docs/development/fdroid.md`). AboutLibraries is GMS-free; the existing
`android-tests.yml` zero-GMS assertion still applies.

License texts the plugin cannot resolve offline are checked in under
`android/config/licenses/` (Apache-2.0, BSD-2-Clause, the Android SDK License
for the GMS dependencies in the `obtainium`/`play` flavors, and SQLCipher's
BSD-style license). Offline mode keeps the build reproducible.

## Tooling evaluation: ORT

The issue asked for an ORT spike first. ORT 97.2.0 was run against the current
tree (`ort analyze`, GoMod + Yarn): it identified the projects correctly and
produced an analyzer result in about 4.5 minutes, with 934 packages. Assembling
full license/copyright notices would require the subsequent `ort scan` stage
(ScanCode) over every package — too heavy for a release-time job, and the
result needs curation for packages with incomplete metadata. The per-ecosystem
fallback in the issue's "Options" table was therefore adopted: Go's own module
graph plus license files, `license-checker` for npm, and AboutLibraries for
Android.

ORT remains a reasonable replacement later if its notice output becomes
stable and its scan cost drops; the committed `THIRD_PARTY_NOTICES.md` and the
drift gate are the contract either way.

## Hand verification

The acceptance criterion was exercised by adding `colors@1.4.0` (MIT) to
`frontend` as a production dependency, regenerating: the npm table gained a
`colors` row and a new MIT license-text entry. Removing the scratch dependency
and regenerating restored the committed file byte-for-byte.

## Relationship to Fossa

This closes the gap that motivated a Fossa evaluation. Fossa's CVE/SBOM
monitoring is already covered by Grype/Syft/Trivy; attribution is now covered
here, so Fossa adds nothing on this axis and is not adopted.
