## Why this exists

A native Android app can reach into things the browser fundamentally can't: call log, SMS, and the
device's own contacts — enabling automated interaction tracking (a real call or text logged as a
cadence-qualifying `Activity` without manual entry, per `91.10`). PWA install already covers "an icon
on the home screen."

### 1.3 openapi-generator invocation

```bash
openapi-generator generate \
  -g kotlin \
  --library jvm-okhttp4 \
  -i backend/openapi.yaml \
  -o android/core/network/src/main/kotlin \
  --additional-properties=\

serializationLibrary=moshi,\
moshiCodeGen=true,\
useCoroutines=false,\
groupId=com.mycorrhizal.crm,\

sourceFolder=.\
  --skip-validate-spec \
  --type-mappings UUID=String \
  --import-mappings UUID=String
```

**Key configuration notes:**

| Setting | Value | Rationale |
|---|---|---|
| `library` | `jvm-okhttp4` | OkHttp is Android-native, works API 21+; Retrofit adds annotation overhead we don't need |
| `dateLibrary` | `kotlinx-datetime` | Kotlin Multiplatform native, avoids java.time backport; `Instant`, `LocalDate`, `LocalDateTime` |
| `serializationLibrary` | `moshi` | Default, stable; Moshi codegen for reflection-free JSON parsing (R8-compatible) |
| `useCoroutines` | `false` | Generated API methods return `Call<T>`; we wrap in suspend functions manually in Repository layer |
| `UUID` mapping | → `String` | Avoids `java.util.UUID` resolution; PK entities already use string UUIDs |

**Spec issues the codegen will encounter (must be pre-fixed or post-processed):**

1. **`allOf` / `oneOf` not supported** by the Kotlin generator. Schemas using these (e.g., `ContactSummaryWithRelations` allOf `ContactSummary`, `CadencePolicyWithHealth` allOf `CadencePolicy`, `CurrentUserResponse` allOf `AdminUserResponse`) must be flattened in the spec OR replaced with hand-written models. Worst case: 7 affected schemas.

2. **`ContactBriefing` schema lacks an explicit `BriefingActivity.type`** — the spec has `type:string` (no enum). Fine for codegen but the Kotlin data class will use `String?` rather than an enum.

3. **`enum` values with special characters** — the `date_format` enum has values like `eu-hyphen` which Kotlin will mangle (→ `EU_HYPHEN`). Acceptable.

4. **Optional vs required fields** are correctly tagged in the spec — the generator will use nullable types (`String?`) correctly.

5. **`date-time` format → `kotlinx.datetime.Instant`**. `date` (date-only) → `kotlinx.datetime.LocalDate`. Both mappings are set via type-mappings.

**Post-generation tasks:**
- Strip generated `build.gradle` (we use our own with version catalog)
- Remove generated README and docs
- Delete the generated `ApiClient.kt`'s auth interceptor — we inject our own that reads from DataStore
- Add `@Serializable` / `@JsonClass(generateAdapter = true)` where Moshi codegen needs it
- Create a `BearerAuthInterceptor` that reads the JWT from `EncryptedSharedPreferences` via DataStore

### 1.4 Hilt module scoping

The DI graph uses Hilt's standard component hierarchy. The critical rule is: bind at the lowest
scope that covers the dependency's lifecycle.

| Scope | Component | What lives here |
|---|---|---|
| `@Singleton` | `SingletonComponent` | `OkHttpClient`, generated `*Api` instances, `RoomDatabase`, `SessionManager` (DataStore wrapper) |
| `@ActivityScoped` | `ActivityComponent` | Nothing by default — prefer `@ViewModelScoped` |
| `@ViewModelScoped` | `ViewModelComponent` | Repositories, DAOs (injected into ViewModels via `@HiltViewModel`) |
| Unscoped | Per-injection | `MobileLinkRegistry` (stateless, created fresh per inject) |

Why repositories are `@ViewModelScoped` and not `@Singleton`:
- Each ViewModel gets its own repository instance, preventing cross-screen state leakage
- Repositories hold no shared mutable state — they're thin wrappers around `*Api` + `*Dao`
- `RoomDatabase` IS `@Singleton` (single connection pool), but DAOs are obtained from it at injection time — the DAO is `@ViewModelScoped`, the database is `@Singleton`

```kotlin
// :core:data module
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides @Singleton
    fun provideOkHttpClient(authInterceptor: AuthInterceptor): OkHttpClient =
        OkHttpClient.Builder()
            .addInterceptor(authInterceptor)
            .addInterceptor(HttpLoggingInterceptor().apply {
                level = if (BuildConfig.DEBUG) BODY else NONE

            .connectTimeout(30, TimeUnit.SECONDS)
            .readTimeout(30, TimeUnit.SECONDS)
            .build()

    @Provides @Singleton
    fun provideContactsApi(client: OkHttpClient): ContactsApi =
        ContactsApi(client) // generated by openapi-generator
}

            .build()

    @Provides
    fun provideCachedContactDao(db: AppDatabase): CachedContactDao = db.cachedContactDao()

    // ... one @Provides per DAO
}

@Module
@InstallIn(ViewModelComponent::class)

    @Provides @ViewModelScoped
    fun provideContactsRepository(api: ContactsApi, dao: CachedContactDao): ContactsRepository =

```

## 2. API client layer (`:core:network` + `:core:data`)

### 2.1 Auth flow

The backend supports two auth paths (from `openapi.yaml`):
- **sessionCookie**: `auth_token` httpOnly cookie → not viable for a native client
- **bearerAuth**: `Authorization: Bearer <token>` — this is the path

Two token types are accepted by the REST layer:
1. **JWT** (from `/login`) — contains `user_id`, `token_version`, `username`. Short-lived (96h default). Invalidated by password change (`User.TokenVersion` bump).
2. **API token** (`mycorrhizal_` prefix) — created via `/api-tokens`, hashed server-side (`SHA-256`). Expires in 90 days (default, max 365). Scope: `full` (REST) or `carddav` (CardDAV only).

**Recommended auth model for the Android client:**

Use **JWT-based session auth** as the primary credential. On first launch:
1. User enters server URL + username + password
2. `POST /api/v1/login` → receives `{ language, date_format }` + sets `auth_token` cookie (which we can't use)
3. The response also sets the JWT in the cookie — but the server also accepts the JWT via `Authorization: Bearer` header
4. Store the JWT in `EncryptedSharedPreferences` (AndroidX Security Crypto)
5. All subsequent requests add `Authorization: Bearer <jwt>` via OkHttp interceptor

**JWT expiry handling:**
- The JWT's `exp` claim is decoded client-side (without verifying signature — the server does that)
- When approaching expiry (< 1 hour), re-authenticate or prompt
- If a 401 is returned, re-login (the token was invalidated by password change)

**API token alternative (longer-lived, power-user path):**
- User generates an API token from the web app Settings
- User enters the token directly in the Android app (no login step)
- Token stored in EncryptedSharedPreferences
- Same `Authorization: Bearer mycorrhizal_<token>` header
- This avoids re-login entirely but ties the session to a single token's lifecycle

### 2.2 OkHttp interceptor chain


### 2.3 Repository pattern

Each API domain gets a Repository that:
- Injects the generated `*Api` interface (e.g., `ContactsApi`, `ActivitiesApi`)
- Wraps `Call<T>` in `suspend` functions via `withContext(Dispatchers.IO)`
- Maps generated DTOs to domain models where needed (for Room persistence)
- Handles error mapping: `ApiError` → domain `Result<T, AppError>`

```kotlin
// Example: ContactsRepository.kt
class ContactsRepository @Inject constructor(
    private val contactsApi: ContactsApi,
    private val contactsDao: ContactsDao,
) {
    suspend fun listContacts(params: ListContactsParams): Result<ContactsPage> = runCatching {
        val response = contactsApi.listContacts(
            cursor = params.cursor,
            limit = params.limit,
            search = params.search,
            circle = params.circle,
            archived = params.archived,
        )
        // Map to domain model + cache in Room
        val page = response.toDomain()
        contactsDao.upsertAll(page.items)
        page
    }
}
```

### 2.4 Error propagation chain

The chain from network to UI has four layers, each with a single responsibility:

```
OkHttp (IOException, HttpException)
    ↓ ApiError sealed hierarchy (parsed from backend Error schema)
Repository (Result<T, AppError>)
    ↓ ViewModel maps to UiState.error: String?
Compose (Snackbar or error card)
```

**ApiError** — a sealed class wrapping every known backend failure:

```kotlin
sealed class ApiError(message: String, cause: Throwable? = null) : Exception(message, cause) {
    val displayMessage: String get() = when (this) {
        is Network -> "No connection"
        is Timeout -> "Request timed out"
        is Server -> "Server error (${code})"
        is Client -> when (code) {
            401 -> "Session expired — please log in again"
            403 -> "You don't have permission"
            404 -> "Not found"
            409 -> message  // "A contact with this email already exists"
            else -> message
        }
        is Parse -> "Unexpected server response"
        is Unknown -> "Something went wrong"
    }
    data class Network(cause: IOException) : ApiError("Network error", cause)
    data class Timeout(cause: SocketTimeoutException) : ApiError("Timeout", cause)
    data class Server(val code: Int, val body: String) : ApiError(body)
    data class Client(val code: Int, override val message: String) : ApiError(message)
    data class Parse(override val message: String) : ApiError(message)
    data class Unknown(cause: Throwable) : ApiError("Unknown error", cause)
}
```

**Repository error mapping** — the `runCatching` block in each repository method catches exceptions
and maps them through a shared `mapError()` extension:

```kotlin
fun Exception.toApiError(): ApiError = when (this) {
    is UnknownHostException, is ConnectException -> ApiError.Network(this as IOException)
    is SocketTimeoutException -> ApiError.Timeout(this)
    is HttpException -> {
        val code = this.code()
        val body = this.response()?.body()?.string() ?: ""
        // Parse the backend's Error schema from JSON
        val parsed = try { moshi.adapter(BackendError::class.java).fromJson(body) } catch (_: Exception) { null }
        val message = parsed?.error?.message ?: body
        if (code in 400..499) ApiError.Client(code, message)
        else ApiError.Server(code, message)
    }
    is JsonDataException -> ApiError.Parse(this.message ?: "Parse error")
    else -> ApiError.Unknown(this)
}

fun <T> Result<T>.foldApiError(
    onSuccess: (T) -> Unit,
    onError: (ApiError) -> Unit,
) {
    fold(
        onSuccess = onSuccess,
        onFailure = { e -> onError((e as? ApiError) ?: ApiError.Unknown(e)) },
    )
}
```

**ViewModel consumption** — every ViewModel's data-loading method follows this pattern:

```kotlin
fun loadContacts() {
    viewModelScope.launch {
        _uiState.update { it.copy(isLoading = true, error = null) }
        contactsRepository.listContacts(buildParams())
            .foldApiError(
                onSuccess = { page ->
                    _uiState.update { it.copy(
                        isLoading = false,
                        contacts = page.items,
                        nextCursor = page.nextCursor,
                    ) }
                },
                onError = { error ->
                    _uiState.update { it.copy(
                        isLoading = false,
                        error = error.displayMessage,
                    ) }
                    // Automatic 401 → force logout
                    if (error is ApiError.Client && error.code == 401) {
                        _events.send(UiEvent.ForceLogout)
                    }
                },
            )
    }
}
```

**UI rendering** — at the Compose layer, `error` is non-null:

```kotlin
val state by viewModel.uiState.collectAsStateWithLifecycle()
LaunchedEffect(state.error) {
    state.error?.let { message ->
        snackbarHostState.showSnackbar(message, actionLabel = "Retry")
        viewModel.onEvent(UiEvent.ClearError)
    }
}
```

### 2.5 Cursor pagination (T17 contract)

Every list endpoint uses the T17 cursor-pagination envelope:
`{ items: [...], next_cursor: string, limit: int, sync?: { mode, ... } }`.
The Kotlin side must implement three mechanics:

**Pagination state:**

```kotlin
data class PaginationState(
    val nextCursor: String? = null,   // null = initial load, "" = end of list
    val limit: Int = 50,
    val isLoadingMore: Boolean = false,
    val hasMore: Boolean = true,
)
```

**Load-next-page in the ViewModel:**

```kotlin
fun loadNextPage() {
    val state = _uiState.value
    if (state.isLoadingMore || !state.pagination.hasMore) return
    viewModelScope.launch {
        _uiState.update { it.copy(pagination = it.pagination.copy(isLoadingMore = true)) }
        contactsRepository.listContacts(
            cursor = state.pagination.nextCursor,
            limit = state.pagination.limit,
            // other filters carried from current state
        ).foldApiError(
            onSuccess = { page ->
                _uiState.update { it.copy(
                    contacts = it.contacts + page.items,
                    pagination = it.pagination.copy(
                        nextCursor = page.nextCursor,
                        isLoadingMore = false,
                        hasMore = !page.nextCursor.isNullOrEmpty(),
                    ),
                    // Apply sync info (incremental deletes)
                ) }
            },
            onError = { /* ... */ },
        )
    }
}
```

**Sync handling** — the `sync` field is a T17 change-feed signal:

```kotlin
data class SyncInfo(
    val mode: SyncMode,
    val incremental: List<String>? = null,  // IDs to delete from local cache
    val fullResync: List<String>? = null,   // reasons for full cache clear
)

sealed interface SyncMode {
    data object Incremental : SyncMode
    data class FullResync(val reason: String) : SyncMode
}
```

When `sync.mode == FullResync`, the Repository clears the entire Room table for that entity and
replaces it with the response items. When `Incremental`, only the listed IDs are deleted.

### 2.6 Response envelope asymmetry

The backend has a deliberate inconsistency that the generated API client will NOT handle:

| Operation | Response shape |
|---|---|
| `POST /contacts` | `{ message: "...", contact: ContactRecordResponse }` (201) |
| `PUT /contacts/:id` | `ContactRecordResponse` (raw object, 200) |
| `POST /relationship-edges` | `{ relationship_edge: RelationshipEdge }` (201) |
| `PUT /relationship-edges/:id` | `RelationshipEdge` (raw object, 200) |
| `POST /circles` | `{ message: "...", circle: Circle }` (201) |
| `PUT /circles/:id` | `Circle` (raw object) |

The generated `*Api` will parse the POST response as-is — it will return the wrapped object or throw
on type mismatch. Each POST repository method must unwrap before returning:

```kotlin
suspend fun createContact(input: ContactRecordInput): Result<ContactRecordResponse> = runCatching {
    val wrapped = contactsApi.createContact(input)
    // The generator typed the return as an inline object — manually extract the contact field
    wrapped.contact  // field name matches the JSON key
}
```

For the generated code to type-check, add a wrapper DTO for each create endpoint that the generator
doesn't know wraps its response. This is a post-generation manual step per create endpoint (roughly
20 endpoints). Document each one in `:core:network/src/main/kotlin/response_wrappers.kt`.

### 2.7 Image loading with Coil

Profile photos and Immich thumbnails use Coil 3 with a custom configuration:

```kotlin
// In :app/Hilt module
@Provides @Singleton
fun provideImageLoader(
    @ApplicationContext context: Context,
    authInterceptor: AuthInterceptor,
): ImageLoader = ImageLoader.Builder(context)
    .components {
        // Add auth headers to every image request (photos require Bearer token)
        add(object : Interceptor {
            override suspend fun intercept(chain: Interceptor.Chain): ImageResult {
                val request = chain.request
                val authedRequest = request.newBuilder()
                    .setHeader("Authorization", "Bearer ${authInterceptor.jwt()}")
                    .build()
                return chain.proceed(authedRequest)
            }
        })
    }
    .memoryCachePolicy(CachePolicy.ENABLED)
    .diskCachePolicy(CachePolicy.ENABLED)
    .diskCache { DiskCache.Builder()
        .directory(context.cacheDir.resolve("coil_cache"))
        .maxSizeBytes(50 * 1024 * 1024) // 50MB
        .build()
    }
    .build()
```

## 3. Room database — local cache & offline read

### 3.1 Schema design

Room mirrors the backend SQLite schema **for readable data only** — it's a cache, not a source of truth. Writes always go to the server first (online-first). Room serves:
- Offline viewing of cached data
- Fast list scrolling without network round-trips
- Full-text search locally (FTS with content sync from server)

- `calendar_subscriptions` / `contact_subscriptions` (server-side sync state)
- `job_executions` (server-only)

### 3.2 DAO patterns

Each DAO supports:
1. `upsertAll(List<T>)` — `@Insert(onConflict = OnConflictStrategy.REPLACE)`
2. `getById(id)` — `@Query` with primary key
3. `getAll()` — cached list (for entity lists: circles, tags, etc.)
4. `getByEntityId(entityId)` — for sub-resources (activities by contact, etc.)
5. `deleteAll()` — cache invalidation
6. `search(query)` — local FTS via `contacts_fts` mirror

### 3.3 Cache invalidation strategy

- Every list response from T17-cursor-paginated endpoints includes a `sync` field: `incremental: [deletedIds]` or `full_resync: [reason]`
- On `full_resync`, clear the table and re-fetch
- On `incremental`, apply deletions
- Room database file size is capped at ~50MB — `deleteAll()` on least-recently-accessed tables when approaching limit

### 3.5 Partial dates (the `CardPartialDate` problem)

The backend uses `contactmodel.PartialDate` with optional `year`, `month`, `day` fields — e.g.,
`{ year: 1990, month: 6, day: 15 }` for a full birthday, `{ month: 12, day: 25 }` for Christmas
(yearly anniversary, year unknown), or `{ year: 2020 }` for "graduated in 2020."

`kotlinx-datetime` has no native partial date type. The Android client defines its own:

```kotlin
@JsonClass(generateAdapter = true)
data class PartialDate(
    val year: Int? = null,
    val month: Int? = null,
    val day: Int? = null,
    val calendarScale: String? = null, // "gregorian" or absent
) {
    /** True if this date has at least a month and day — can be rendered as "June 15." */
    val hasMonthDay: Boolean get() = month != null && day != null

    /** True if only a year is known — render as "2020." */
    val isYearOnly: Boolean get() = year != null && month == null

    /**
     * Format for display using the user's DateFormat preference.
     * Full date: "15 June 1990" (eu), "June 15, 1990" (us)
     * Month+day only: "25 December"
     * Year only: "2020"
     * Yearless month+day: rendered as "--12-25" in vCard, shown as "25 December" in UI
     */
    fun display(format: DateFormat): String = when {
        year != null && hasMonthDay -> formatDate(year!!, month!!, day!!, format)
        hasMonthDay -> "${dayOfMonth(day!!)} ${monthName(month!!)}"  // yearless
        isYearOnly -> "$year"
        else -> ""
    }
}
```

The Room `TypeConverter` stores `PartialDate` as a JSON string (same Moshi adapter pattern). The
`LifeEvent.date` and `Anniversary.date.partial` fields use this type.

### 4.5 Client-side form validation mirroring backend validators

The backend registers custom `go-playground/validator` tags that the frontend mirrors as
hand-written enums (per `/CLAUDE.md`'s frontend trap 4). The Android client must do the same.
These are hand-maintained Kotlin copies of the backend validator logic:

```kotlin
object Validators {
    /** Backend `phone` validator: must start with `+` or digit, min 4 chars after stripping non-digits. */
    fun isValidPhone(value: String): Boolean {
        val digits = value.replace(Regex("[^+0-9]"), "")
        return digits.isNotEmpty() && digits.length >= 4 && (digits.startsWith("+") || digits.first().isDigit())
    }

    /** Backend `birthday` validator: YYYY-MM-DD or --MM-DD, valid calendar date. */
    fun isValidBirthday(value: String): Boolean {
        val pattern = Regex("""^(\d{4}|--)?(\d{2})-(\d{2})$""")
        val match = pattern.matchEntire(value) ?: return false
        val (_, monthStr, dayStr) = match.destructured
        val month = monthStr.toInt()
        val day = dayStr.toInt()
        return month in 1..12 && day in 1..31
    }

    /** Backend `safeurl` validator: HTTP/HTTPS only, no javascript:, no SSRF-risky schemes. */
    fun isValidSafeUrl(value: String): Boolean {
        return try { URI(value).let { it.scheme.let { s -> s == "http" || s == "https" } } }
            catch (_: Exception) { false }
    }
}
```

| Multiple repositories combined (contact + activities) | Yes — `GetContactBriefingUseCase` | Orchestrates `ContactRepository` + `ActivityRepository` + `CadenceRepository` |
| Business rule enforcement | Yes — `CreateContactUseCase` | Validates input, checks for duplicates, applies sensitivity defaults |
| Cross-cutting concern | Yes — `SyncPendingInteractionsUseCase` | Reads from Room `PendingInteraction` table, writes to `ActivityRepository`, marks synced |

### 6.1 Call log tracking — `CallLog.Calls`

**Permissions required:**
- `READ_CALL_LOG` (runtime, dangerous)
- `READ_PHONE_STATE` (runtime, dangerous — for detecting ongoing calls)
- `READ_CONTACTS` (for matching phone numbers to contacts)

**Architecture:**

```
PhoneStateReceiver (BroadcastReceiver)
    ↓ onReceive(Intent) → PHONE_STATE = IDLE (call ended)
    ↓
CallLogWorker (WorkManager OneTimeWorkRequest)
    ↓ reads CallLog.Calls content provider for the last call
    ↓ matches phone number against local contacts DB
    ↓
CallSuggestionRepository
    ↓ creates PendingInteraction(call) → stores in Room
    ↓
InteractionSyncWorker (WorkManager PeriodicWorkRequest, 15min)
    ↓ syncs pending interactions to server as Activity rows
    ↓ marks as synced
```

**`CallLog.Calls` query:**

|---|---|
| `INCOMING_TYPE` | `call` |

### 6.2 SMS tracking — `Telephony.Sms`

**Permissions:** `READ_SMS` (runtime, dangerous) + `RECEIVE_SMS` (for real-time detection)

**Architecture:**
```
SmsReceiver (BroadcastReceiver, priority LOW so user's SMS app gets it first)
    ↓ onReceive(Intent) → reads SMS from Intent extras
    ↓ extracts: address (phone number), body (content), date
    ↓ matches phone number against local contacts DB
    ↓
SmsSuggestionRepository
    ↓ creates PendingInteraction(message) → stores in Room
    ↓
InteractionSyncWorker → same as call tracking
```

Activity type: `message`

**SMS privacy consideration:** Only metadata (phone number, timestamp) is captured; message body is used for on-device contact matching only and is **never sent to the server** (the server sees `Activity.title = "Message with [Contact Name]"`, `Activity.description = null`). This is a deliberate privacy boundary.

### 6.3 BroadcastReceiver registration

| Receiver | Intent Filter | Registration | Notes |
|---|---|---|---|
| `PhoneStateReceiver` | `PHONE_STATE` | Manifest (required for this intent) | Only triggers `IDLE` → off-hook → `IDLE` = call ended |
| `SmsReceiver` | `SMS_RECEIVED` / `SMS_DELIVER` | Manifest, priority=0 | Low priority so default SMS app processes first |
| `BootReceiver` | `BOOT_COMPLETED` | Manifest | Re-registers periodic WorkManager workers |
| `ConnectivityReceiver` | `CONNECTIVITY_CHANGE` | Context-registered in Application | Triggers sync when network becomes available |

### 6.4 WorkManager jobs

| Worker | Type | Interval | What it does |
|---|---|---|---|
| `CallLogSyncWorker` | `OneTime` | Triggered by BroadcastReceiver | Reads recent calls, creates PendingInteractions |
| `InteractionSyncWorker` | `Periodic` | 15 min (min interval) | Syncs PendingInteractions → server as Activities |
| `ContactCacheSyncWorker` | `Periodic` | 6 hours | Full re-sync of Room cache with server (change feed) |
| `ReminderNotificationWorker` | `Periodic` | 1 hour | Checks upcoming reminders, posts Android notifications |
| `CadenceCheckWorker` | `Periodic` | 4 hours | Checks overdue cadences, posts Android notifications |
| `BirthdayCheckWorker` | `Periodic` | 24 hours | Checks upcoming birthdays, posts notifications |
| `DataCleanupWorker` | `Periodic` | 7 days | Trims Room DB (old synced interactions, expired cache) |

### 6.5 Quick-capture overlay — `SYSTEM_ALERT_WINDOW`

A floating action button (FAB) overlay that lets the user log an interaction *during* or *right after* a call, without switching apps.

**Permission:** `SYSTEM_ALERT_WINDOW` (special, must be granted in Settings)

**Architecture:**
```
CallDetectionService (Foreground Service with notification)
    ├── Listens for PHONE_STATE changes
    ├── When call ends → shows QuickCaptureOverlay for 30 seconds
    └── If user taps overlay → QuickCaptureSheet opens
        ├── Pre-filled: contact matched from phone number
        ├── Activity type: call (auto-selected)
        ├── Optional: notes / description
        └── "Save" → writes Activity to server immediately
```

**Key design decisions:**
- The overlay is opt-in (requested on first call detection, not auto-enabled)
- The overlay is a `WindowManager.LayoutParams.TYPE_APPLICATION_OVERLAY` with `FLAG_NOT_FOCUSABLE` + `FLAG_NOT_TOUCH_MODAL`
- The foreground service is required (Android 8+ background execution limits)
- The service kills itself after 5 minutes of no call activity to conserve battery

### 6.7 Foreground service lifecycle — `CallDetectionService`

The quick-capture overlay (6.5) runs inside a foreground service to stay alive during and
shortly after calls. Android 14+ enforces foreground service type declarations:

```xml

<uses-permission android:name="android.permission.FOREGROUND_SERVICE_PHONE_CALL" />

<service
    android:name=".feature.capture.CallDetectionService"
    android:foregroundServiceType="phoneCall"
    android:exported="false" />
```

**Service lifecycle:**

```kotlin
@AndroidEntryPoint
class CallDetectionService : Service() {
    @Inject lateinit var callLogRepository: CallLogRepository
    @Inject lateinit var notificationManager: CallDetectionNotificationManager

    private val phoneStateListener = object : PhoneStateListener() {
        private var lastState = TelephonyManager.CALL_STATE_IDLE

        override fun onCallStateChanged(state: Int, phoneNumber: String?) {
            when {
                // Call just ended: ring → off-hook → idle transition
                state == TelephonyManager.CALL_STATE_IDLE && lastState == TelephonyManager.CALL_STATE_OFFHOOK -> {
                    phoneNumber?.let { onCallEnded(it) }
                }
            }
            lastState = state
        }
    }

    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val notification = notificationManager.buildOngoingNotification()
        startForeground(CALL_DETECTION_NOTIFICATION_ID, notification)

        val telephonyManager = getSystemService(TelephonyManager::class.java)
        telephonyManager.listen(phoneStateListener, PhoneStateListener.LISTEN_CALL_STATE)

        // Self-stop after 5 minutes of no call activity
        handler.postDelayed({ stopSelf() }, 5 * 60 * 1000L)

        return START_STICKY
    }

    private fun onCallEnded(phoneNumber: String) {
        // 1. Match phone number to a Mycorrhizal contact
        // 2. Store PendingInteraction in Room
        // 3. Show the quick-capture overlay (if user enabled it)
        // 4. Extend the self-stop timer
        handler.removeCallbacksAndMessages(null)
        handler.postDelayed({ stopSelf() }, 5 * 60 * 1000L)
    }

    override fun onDestroy() {
        handler.removeCallbacksAndMessages(null)
        val telephonyManager = getSystemService(TelephonyManager::class.java)
        telephonyManager.listen(phoneStateListener, PhoneStateListener.LISTEN_NONE)
        super.onDestroy()
    }

    override fun onBind(intent: Intent?): IBinder? = null

    companion object {
        private const val CALL_DETECTION_NOTIFICATION_ID = 1001
    }
}
```

**Ongoing notification** (required for foreground services, Android 8+):

```kotlin

}
```

#### 7.5.2 MIMETYPE → Card field + link action mapping

Each `Data` row's `MIMETYPE` maps to a Card field and one or more Android Intents:

| MIMETYPE | Card field | Link action(s) | Intent |
|---|---|---|---|
| `vnd.android.cursor.item/phone_v2` | `CardPhone` | Call (`tel:`) | `Intent.ACTION_DIAL`, `Uri.parse("tel:$number")` |
| | | Text (`sms:`) | `Intent.ACTION_SENDTO`, `Uri.parse("smsto:$number")` |
| | | Copy | `ClipboardManager.setText("phone", number)` |
| `vnd.android.cursor.item/email_v2` | `CardEmail` | Compose (`mailto:`) | `Intent.ACTION_SENDTO`, `Uri.parse("mailto:$address")` |
| | | Copy | `ClipboardManager.setText("email", address)` |
| `vnd.android.cursor.item/postal-address_v2` | `CardAddress` | Map (`geo:`) | `Intent.ACTION_VIEW`, `Uri.parse("geo:0,0?q=$formattedAddress")` |
| | | Copy (formatted) | `ClipboardManager.setText("address", formatted)` |
| `vnd.android.cursor.item/im` | `CardOnlineService` | Copy only | No standard Android intent for arbitrary IM protocols |
| `vnd.android.cursor.item/website` | `CardResource` (link) | Open in browser | `Intent.ACTION_VIEW`, `Uri.parse(url)` |
| | | Copy | `ClipboardManager.setText("url", url)` |
| `vnd.android.cursor.item/organization` | `CardOrganization` + `CardTitle` | Copy only | Structured data, no intent |

**Phone feature detection** (T34's "multi-action field" pattern):
- The `CommonDataKinds.Phone.TYPE` column (DATA2) carries the label: `TYPE_MOBILE` gets both `tel:` and `sms:` buttons; `TYPE_FAX` gets copy only; everything else gets `tel:` + copy. Landline vs. mobile distinction is best-effort — Android doesn't expose a hard "is this a mobile device" flag.

#### 7.5.4 Native Contacts app cross-reference

For contacts that exist in **both** the Mycorrhizal server and the device's native Contacts app
(e.g., after a T57 import that wasn't a delete-from-device), a `ContactsContract.Data` lookup
can find the device-side `CONTACT_ID` and offer an "Open in Contacts" action. This is a
`ContactsContract.QuickContact` badge or an overflow menu item, optionally displayed when
`READ_CONTACTS` is granted — useful for contacts with large notes, custom ringtones, or other
device-native data fields not mapped into Mycorrhizal.

```kotlin
fun findDeviceContactId(
    resolver: ContentResolver,
    lookupKey: String? = null,
    phoneNumber: String? = null,
    email: String? = null,
): Long? {
    // Try lookup key first (if this was a T57 import, we stored it)
    if (lookupKey != null) {
        resolver.query(
            ContactsContract.Contacts.CONTENT_URI,
            arrayOf(ContactsContract.Contacts._ID),
            "${ContactsContract.Contacts.LOOKUP_KEY} = ?",
            arrayOf(lookupKey),
            null
        )?.use { cursor ->
            if (cursor.moveToFirst()) return cursor.getLong(0)
        }
    }
    // Fall back to Data query by phone/email
    val selection = buildString {
        if (phoneNumber != null) {
            append("${ContactsContract.Data.MIMETYPE} = ? AND ${ContactsContract.Data.DATA1} = ?")
        }
        if (email != null) {
            if (isNotEmpty()) append(" OR ")
            append("${ContactsContract.Data.MIMETYPE} = ? AND ${ContactsContract.Data.DATA1} = ?")
        }
    }
    val selectionArgs = buildList {
        if (phoneNumber != null) {
            add(ContactsContract.CommonDataKinds.Phone.CONTENT_ITEM_TYPE)
            add(phoneNumber)
        }
        if (email != null) {
            add(ContactsContract.CommonDataKinds.Email.CONTENT_ITEM_TYPE)
            add(email)
        }
    }
    if (selection.isEmpty()) return null
    resolver.query(
        ContactsContract.Data.CONTENT_URI,
        arrayOf(ContactsContract.Data.CONTACT_ID),
        selection,
        selectionArgs.toTypedArray(),
        "${ContactsContract.Data.CONTACT_ID} ASC LIMIT 1"
    )?.use { cursor ->
        if (cursor.moveToFirst()) return cursor.getLong(0)
    }
    return null
}
```

#### 7.5.5 Integration with T57 import and ongoing contact matching

During T57 import, the `LOOKUP_KEY` from `ContactsContract.Contacts` is stored alongside the
Room-cached contact. This key is stable across contact renames and aggregations (unlike
`CONTACT_ID`) and enables:
1. **Post-import deduplication check**: if the user re-imports later, the `LOOKUP_KEY` prevents
   creating a duplicate Mycorrhizal contact for the same device contact.
2. **"Open in Contacts" action**: the `LOOKUP_KEY` resolves to a `CONTENT_LOOKUP_URI` for
   `QuickContact.showQuickContact()`.
3. **Call/SMS contact matching**: when a phone number matches against `ContactsContract.Data` with
   MIMETYPE `phone_v2`, the row's `CONTACT_ID` points to the device-side contact, and the stored
   `LOOKUP_KEY` links it to the Mycorrhizal contact — confirming the match.

The `LOOKUP_KEY` is stored in Room as an additional column on `CachedContact`:

```kotlin
@Entity(tableName = "cached_contacts")
data class CachedContact(
    @PrimaryKey val id: Int,
    val uid: String,
    val deviceLookupKey: String? = null,  // from ContactsContract, null if not imported
    // ... all other columns
)
```

#### 7.5.6 Permission scoping for link actions

| Action | Permission required | Notes |
|---|---|---|
| `ACTION_DIAL` (`tel:`) | None | `ACTION_DIAL` opens the dialer with number pre-filled, does not place the call — no permission needed. `ACTION_CALL` (direct dial) requires `CALL_PHONE` and is not used. |
| `ACTION_SENDTO` (`sms:`, `mailto:`) | None | Opens the SMS or email app with the recipient pre-filled |
| `ACTION_VIEW` (`geo:`) | None | Opens a maps app |
| `ACTION_VIEW` (URL) | None | Opens the browser |
| Copy to clipboard | None | Managed by `ClipboardManager` |
| `QuickContact` badge | `READ_CONTACTS` | Only shown when permission is granted and a `LOOKUP_KEY` match exists |
| `ContactsContract.Data` queries | `READ_CONTACTS` | Used for cross-reference and import; not needed for basic link actions |

### 7.6 Mobile link action enrichment — third-party app actions from ContactsContract.Data

The web app's `LinkFieldType` model (T34) is a flat registry: one entry per service, with a single
`protocol` string. But on Android, `ContactsContract.Data` exposes a richer reality:

- **Third-party apps register custom MIMETYPEs** — Signal, WhatsApp, Telegram, Google Meet, etc.
  each contribute data rows under MIMETYPEs like `vnd.android.cursor.item/vnd.com.whatsapp.voip.call`.
- **One app can expose multiple action types** — Signal alone has distinct MIMETYPEs for message,
  voice call, and video call. WhatsApp distinguishes `voip.call` from `video.call` from plain `profile`.
- **Action availability is device-specific** — an app's MIMETYPE only appears in `Data` rows if
  the app is actually installed.

The existing `LinkFieldType.protocol` field (a single string like `"signal"` or `"whatsapp"`)
cannot express this multiplicity, and the server has no way to know which apps are installed on
a given device. So the server owns the **existence** of the link ("Alice uses Signal, her handle is
`alice.42`"), while the Android client owns the **actions** ("how do I reach Alice on Signal —
message, voice call, or video call?").

#### 7.6.1 Design decision: client-side enrichment, no backend change

The `LinkFieldType` model on the server stays as-is. The Android client augments each link field
at display time by consulting two sources:

1. **A client-side registry** — a hand-maintained map from well-known `LinkFieldType.protocol`
   values to sets of `MobileLinkAction` objects. This is the Android equivalent of the frontend's
   hardcoded enum mirror convention: it must stay in sync with the `LinkFieldType` defaults the
   server seeds, plus any entries the user's own server instance has created.
2. **A live `ContactsContract.Data` query** — for a given contact's handles (phone numbers, online
   service user IDs), the client checks whether the device has MIMETYPE rows for the corresponding
   services. This gates action display: a "Signal Voice Call" button only appears if Signal is
   installed AND the contact has a reachable handle.

#### 7.6.4 Runtime resolution — which actions are actually available

At display time, for a given contact's link field, the client resolves which actions to show by
intersecting the registry's `mimeTypes` against the device's actual `ContactsContract.Data` rows:

```kotlin
suspend fun resolveAvailableActions(
    resolver: ContentResolver,
    handle: String,              // the contact's handle on this service (phone number, username)
    linkType: MobileLinkType,
): List<MobileLinkAction> = withContext(Dispatchers.IO) {
    // Build a MIMETYPE filter from the union of all action mimeTypes for this link type
    val allMimeTypes = linkType.actions.flatMap { it.mimeTypes }.distinct()
    if (allMimeTypes.isEmpty()) return@withContext emptyList()

    // Query ContactsContract.Data for any rows matching these MIMETYPEs
    val installedMimeTypes = mutableSetOf<String>()
    resolver.query(
        ContactsContract.Data.CONTENT_URI,
        arrayOf(ContactsContract.Data.MIMETYPE),
        "${ContactsContract.Data.MIMETYPE} IN (${allMimeTypes.joinToString(",") { "?" }})",
        allMimeTypes.toTypedArray(),
        null,
    )?.use { cursor ->
        while (cursor.moveToNext()) {
            installedMimeTypes.add(cursor.getString(0))
        }
    }

    // A MIMETYPE being present in the Data table means the app is installed.
    // Filter linkType.actions to those where ALL required mimeTypes are present.
    linkType.actions.filter { action ->
        action.mimeTypes.any { it in installedMimeTypes }
    }.also {
        // If no MIMETYPE matched but the user added this link manually,
        // fall back to the first action (APP_OPEN) — the app may still be installed
        // but not registered in the Data table for this contact.
    }
}
```

#### 7.6.6 User-extensible entries

A user who creates a custom `LinkFieldType` (e.g., "Matrix" with `protocol: "matrix"`) gets no
actions by default (the client-side registry doesn't know about it). The app provides a
"Custom link actions" editor in Settings where the user can add one or more MIMETYPE + intent
URI template pairs per custom link type — these are stored locally in Room, not synced to the
server.

```kotlin

    @PrimaryKey(autoGenerate = true) val id: Int = 0,
    val protocol: String,          // matches LinkFieldType.protocol
    val label: String,
    val kind: String,              // MobileActionKind.name
    val mimeTypes: List<String>,   // JSON-encoded via TypeConverter
    val intentUriTemplate: String, // e.g., "matrix://chat?user={handle}"
)
```

#### 7.6.7 Why this isn't a backend change

| Concern | Server-side | Client-side |
|---|---|---|
| Link existence (Alice uses Signal) | `LinkFieldType` row + `OnlineService` on Card | Rendered from API data |
| Action multiplicity (message, call, video) | Not expressible in current model | `MobileLinkRegistry` |
| App installed on this device? | Can't know | `ContactsContract.Data` MIMETYPE query |
| Custom app deep-link URIs | Would be Android-specific pollution | Local `CustomLinkAction` table |
| Other clients (web, iOS) | Render as single tappable link | No change needed |

The only backend consideration for a future design pass: if multiple actions per link type
becomes a pattern other clients want to consume (e.g., an iOS client with CallKit integration),
a `LinkFieldAction` sub-table would be warranted. But that's a v2 concern — the current
client-side registry avoids premature generalization.

- **Overlay**: Toggle switch → "Draw over other apps" → system settings intent → on return, check if granted

Denied permissions are gracefully degraded (the feature is simply unavailable, no nag screens).

## 9. Security considerations

### 9.1 Credential storage

- JWT and API tokens stored in `EncryptedSharedPreferences` (AES-256 GCM, key in Android Keystore backed by TEE)
- Server URL stored in plain DataStore (not sensitive)
- Never log the JWT or token

### 9.2 Certificate pinning

For self-hosted instances (the primary deployment model), users are connecting to their own server with a self-signed or custom CA certificate. Options:
- **Recommended**: User imports the server's CA certificate during setup (Android's `KeyChain.createInstallIntent()`)
- **Fallback**: `network_security_config.xml` with a debug override for user-specified certificate SHA-256 pins
- **Not supported**: disabling TLS verification (never shipped)

### 9.3 Data at rest

- Room database file is stored in the app's internal storage (`/data/data/.../databases/`) — already sandboxed by Android
- No additional encryption layer for Room (the cached data is only as sensitive as the contacts it mirrors)
- Phone numbers and SMS content used for contact matching never leave the device; only structured Activity rows (title, date, type) are sent to the server

### 9.4 ProGuard / R8

- Moshi `@JsonClass(generateAdapter = true)` models must be kept
- Room entities, DAOs, and `TypeConverter`s must be kept
- OkHttp, generated API classes, and data classes must be kept
- `proguard-rules.pro` additions for all generated code

### 9.5 TLS certificate trust for self-hosted servers

The primary deployment model is self-hosted (Docker). Users often run with a self-signed
certificate or a custom CA. Android's default trust store rejects these. The app supports
three trust models via `network_security_config.xml`:

```xml
<!-- :app/src/main/res/xml/network_security_config.xml -->
<network-security-config>
    <!-- Production: system CAs only (default Android behavior). -->
    <base-config cleartextTrafficPermitted="false">
        <trust-anchors>
            <certificates src="system" />
        </trust-anchors>
    </base-config>

    <!-- User-added CAs: enabled only in debug builds, not production.
         User can install their self-signed CA via Settings → Security → Install certificate
         and the debug build will trust it. -->
    <debug-overrides>
        <trust-anchors>
            <certificates src="system" />
            <certificates src="user" />
        </trust-anchors>
    </debug-overrides>
</network-security-config>
```

For production use with a self-signed cert, the user imports the cert at setup time via
Android's `KeyChain` API:

```kotlin
suspend fun installCustomCertificate(context: Context, certBytes: ByteArray): Result<Unit> {
    val intent = KeyChain.createInstallIntent().apply {
        putExtra(KeyChain.EXTRA_CERTIFICATE, certBytes)
        putExtra(KeyChain.EXTRA_NAME, "Mycorrhizal Server")
    }
    context.startActivity(intent)
    // User must approve the install in the system dialog — no programmatic install.
    return Result.success(Unit)
}
```

The certificate pinning fallback from section 9.2 provides a second layer for users who
prefer pinning over the KeyChain flow. The app never ships with "disable TLS verification"
as an option — that would make the credential in transit interceptable.

**AndroidManifest reference:**

```xml
<application
    android:networkSecurityConfig="@xml/network_security_config"
    ...>
```

## 10. Testing strategy

The existing project's test conventions (from `/CLAUDE.md`) are:

- **Hand-verify every test** — break the code, confirm the test fails, restore. A test that has never failed has proven nothing.

### 10.7 Hand-verification protocol (from `/CLAUDE.md`, adopted for Android)

For every new test:
1. Write the test, run it, confirm it passes against the working code
2. Break the code the test exercises (e.g., remove a `user_id` filter, swap a condition, delete a permission check)
3. Run the test, **confirm it fails** with the expected failure message
4. Restore the code, confirm the test passes again

A test that has never failed has proven nothing. This is the project's single most important testing rule and applies to the Android codebase exactly as it does to the Go backend and React frontend.

## 12. Open questions (carried from the original stub)

These remain unresolved — they're design decisions for the implementation phase, not blockers for scoping:

1. **Contact matching for call/SMS**: How to match a phone number to a Mycorrhizal contact when a contact has multiple phone numbers or the number is formatted differently (international prefix, spaces, dashes). Needs a normalized phone number comparison function.

2. **Suggest-vs-auto-log**: Does auto-tracked call/SMS data land as confirmed `Activity` rows or as `P2`-style suggestions requiring user review? The M1 stub leans "suggestion-first" — this document assumes that, with `PendingInteraction` as the local staging table.

3. **Auth token lifecycle**: If using JWT (96h expiry), the app needs a seamless re-login flow. If the user's password changes, the token is invalidated server-side (`token_version` bump) but the client won't know until a 401. Should we poll `/users/me` periodically?

4. **Multi-device contact matching**: If the user has the Android app and the web app open simultaneously, two devices could create duplicate Activities for the same call (if both detect it). Needs a deduplication key (call timestamp + phone number hash).

5. **FCM vs WorkManager for notifications**: The web app uses VAPID push (N9). Android could use FCM for real-time reminder push from the server, eliminating the polling `ReminderNotificationWorker`. But FCM requires Google Play Services and a server-side FCM integration that doesn't exist yet. Polling is simpler for a self-hosted deployment.

6. **Offline writes**: If the device is offline, writes (new contacts, activities) are queued and synced when connectivity returns. Conflict resolution when two devices modify the same contact offline is undefined — for a single-user instance this is unlikely, but it should be documented as "last-write-wins."

### Deliberate deviations from the design (recorded for the reviewer)

1. **Hand-written API client, not openapi-generator output.** The §1.3 generator pass is deferred:
   the spec's `allOf`/`oneOf` schemas (noted in §1.3 as needing pre-fixing) aren't flattened yet,
   and Phase 1 only needs login/me/contacts. `:core:network`'s `ApiClient` is small and
   endpoint-focused, so swapping in generated code later is a local replacement. Also uses Moshi
   `@JsonClass` codegen via `KotlinJsonAdapterFactory` (the library-sanctioned discovery path for
   R8-friendly generated adapters) rather than manual adapter registration.
2. **Room entities live in `:core:data`, not `:core:model`.** The §1.2 layout puts entities in the
   model module, but model is deliberately dependency-free and Room annotations are an Android
   concern; keeping entities with their DAOs in data is the standard layering and keeps the
   module graph clean.
3. **Repositories are `@Singleton`, not `@ViewModelScoped`.** They are stateless wrappers over
   `ApiClient` + DAO + `SessionManager` with no mutable UI state, so the scopes are functionally
   identical; noted in `DataModule`'s doc comment. Revisit if a repository ever grows per-session
   in-memory state.
4. **JUnit 4, not JUnit 5.** Robolectric + Compose `createComposeRule` are JUnit4-native; the
   ticket's own §10.3/§10.5 samples use `@RunWith(AndroidJUnit4::class)`. Turbine/MockK are
   framework-agnostic.
5. **Validators mirror the backend exactly, including `omitempty` semantics.** The §4.5 snippets
   for `phone`/`birthday`/`safeurl` diverge from `backend/middleware/validation.go` (which has a
   `safeurl` *blocklist* and a separate `httpurl` *allowlist*, plus 5–20 digit phone and no
   day-range birthday check). The Android copies match the server byte-for-byte so the client
   never rejects a value the server accepts.
6. **Search, notes, activities, home tabs are placeholders.** Bottom-nav scaffold exists
   (§4.1); only Contacts has content in Phase 1.
