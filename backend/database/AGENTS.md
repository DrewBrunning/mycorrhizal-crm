# Database — migrations, schema, backup/restore

Read the root `AGENTS.md` and `backend/AGENTS.md` first (trap #1 is the real-migrated-schema rule;
traps #7 and #9 cover delete semantics and SQLite locking). This file covers the migration chain,
the supported upgrade floor, and the schema artifacts.

## Migrations

- Migration files are **hand-written SQL up/down pairs** in `backend/database/migrations/`. The
  schema does **not** come from GORM `AutoMigrate`; never add a column by editing a model struct
  alone. Add the `.up.sql`/`.down.sql` pair and update the model + `models/schema_parity_test.go`.
- The server runs every pending migration on startup (`database.InitDB`, from an embedded FS).
  `make migrate-up` is only for migrating a database without booting the app.
- `make migrate-down` rolls back **exactly one** migration and prompts first. It is destructive — it
  runs that migration's `.down.sql`. Both the CLI and the Makefile read `SQLITE_DB_PATH`, so they
  target the same database the server does. Never reintroduce the old "roll back every migration"
  behaviour; with the squashed baseline it destroyed the whole schema.
- **The chain is append-only and frozen.** Never edit a shipped migration; add a new one. The
  committed per-release schema dumps are the frozen history the upgrade matrix tests against.
- `_txlock=immediate` in the DSN is load-bearing (backend trap #9). Do not remove it.

## Production data and the upgrade floor

Real production data exists. A migration that renames/drops/retypes a column needs a real backfill
or an explicit, deliberate call that the data is safe to lose — ask when in doubt. Soft-deleted rows
are user data, not test fixtures; be careful with the cascade lists and the retention/purge windows.

Supported in-place upgrades are bounded (issue #529): **from `v1.0.0` (migration `000057`) and
later**, with version-skipping in range supported. The longest skip (`v1.0.0 → current`) and every
adjacent hop are tested in CI from the committed per-release dumps
(`backend/database/testdata/schemas/`, generated by `cmd/genschema` from the append-only chain). A
database below the floor **refuses to migrate** on startup with a two-step message naming `v1.0.0` —
never a best-effort single hop. The single known sub-floor instance (the maintainer's
`v0.2.0-alpha-candidate`) gets a one-time documented bridge
(`MYCORRHIZAL_ALLOW_SUB_FLOOR_MIGRATION=1`); see `docs/upgrade-compatibility.md`. Do not add a second
exception without changing the policy.

Cutting a release does the registration: dispatch `.github/workflows/release.yml` with the version,
and it appends `internal/schemafixture.SupportedReleases`, runs `go run ./cmd/genschema`, commits the
dump to `main`, and tags. By hand: add to `SupportedReleases`, run `genschema`, commit the dump. The
completeness test and the `docker-publish` release gate fail until the dump exists.
`migration-tests.yml`'s upgrade matrix derives its legs from `SupportedReleases` via
`cmd/releaselist`, so a new release is covered with no workflow edit.

## Backup and restore

Backup/restore is an operator-facing data-preservation path
(`docs/security/data-retention-lifecycle.md`, `docs/operations/disaster-recovery.md`). The
pre-migration backup and the restore drill are part of the upgrade safety story; a change to either
gets the same care as a migration. `go run ./cmd/backup` / `cmd/backupverify` are the tooling, and
the migration/deploy gates exercise them. Never make a migration depend on a backup having been
taken unless the preflight actually enforces it.
